# 0005 — Netlify

Status: accepted
Date: 2026-09-12
Answers: `docs/02-project-structure.md` §11 question 5

## Decision

Netlify, over Cloudflare Pages.

## Why

Forms. The Contact page (audit §5.6) and the burnout-check lead magnet (audit
appendix D) both need somewhere to POST, and Netlify Forms handles that with an
attribute on the `<form>` element — no backend, no third-party vendor, no extra
credentials. On Cloudflare Pages the same two forms mean adding Formspree.

Cloudflare Pages is the faster CDN, but this is a seven-page static site of a few
hundred KB. The performance difference will not be measurable against the audit
§10 targets; the forms difference is two vendors versus one.

Deploy previews per pull request are the other reason: it is how John reviews a
page before it goes live, which matters more here than usual because he cannot
edit the site himself (ADR 0002).

## Consequences

- `netlify.toml` holds the build command, publish directory and Node version.
  Node is pinned there as well as in `package.json` `engines` — Netlify reads its
  own config, not `engines`.
- Redirects live in `public/_redirects`, which Astro copies to `dist/` verbatim.
  Audit appendix A's URL map goes there.
- Forms are `data-netlify="true"` with a honeypot. Submissions land in the
  Netlify dashboard and email John; the burnout-check PDF delivery still needs an
  ESP (audit §11 / appendix D) and is not wired yet.
- Nothing in the build is Netlify-specific. Moving to Cloudflare later means
  swapping two forms to Formspree and translating `_redirects`, not a rebuild.

## Still needed from Andrew

Connecting the repo to Netlify is a dashboard step with credentials — it cannot
be done from here. Once connected, the DNS cutover in audit §7 applies.
